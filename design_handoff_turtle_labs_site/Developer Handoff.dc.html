Turtle Labs Website

Everything needed to take this design from a working prototype to a live, database-backed website. Written for two readers: a developer (Sections 3-6) and a non-coder founder (Section 7). Start with Section 1.

1. What you have

A complete, high-fidelity front-end built in HTML/CSS/JavaScript (React under the hood). Every screen, flow, animation and interaction is finished and clickable. What is not yet built: the server, the database, real email sending, and login. Those are Section 4 onward.

2. Run it locally (any machine)

Because the pages load a shared script and images, opening the HTML by double-click will not work. Serve the folder over a tiny local web server instead. Pick whichever you have.

Option A - Python (already on most Macs/Linux)

cd path/to/project
python3 -m http.server 8000

Then open http://localhost:8000/Turtle%20Labs%20Landing.dc.html

Option B - Node (if you have Node.js)

cd path/to/project
npx serve .          # or:  npx http-server -p 8000

Option C - VS Code

Install the Live Server extension, right-click any .dc.html file, choose Open with Live Server.

Filenames have spaces (e.g. Turtle Labs Landing.dc.html). In a URL a space becomes %20. Before real hosting, rename files to hyphenated slugs (index.html, works.html, journal.html) and update the links between pages.

3. Architecture at a glance

Browser (the .dc.html pages)
        |
        |  reads content from
        v
   tl-content.js   <--- TODAY: hand-edited file
        |
        |  TARGET: replace this static file with a live API call
        v
   Backend API  --->  Database (works, journal, reviews, logos, leads)
        |
        +-->  File / media storage (images, video, PDFs)
        +-->  Email service (workbook, playbook, booking confirmations)
        +-->  Auth (real CMS login)

The whole backend job is: stand up a database + API, then swap the one import('./tl-content.js') call for a fetch() to that API, and make the CMS write to it instead of memory.

4. Connecting a backend & database

Recommended stack for a solo project: Supabase (hosted Postgres database + file storage + auth + auto-generated API, generous free tier). Firebase is an equal alternative. Steps are the same in spirit.

1
Create the project. Sign up at supabase.com, create a project, note the Project URL and the public (anon) API key.
2
Create tables that mirror tl-content.js: works, journal, reviews, logos, plus featured (ordered work ids) and leads (captured emails). Match the field names already used in tl-content.js so the front-end needs minimal changes.
3
Enable Storage for media (images, video, PDFs). Store the public URL of each upload in the matching row (e.g. a work's media array).
4
Point the site at it. In each page's componentDidMount, replace the import('./tl-content.js') block with a fetch of the same shape:
// BEFORE (static file)
import('./tl-content.js').then(m => { this._shared = m.TL_CONTENT; ... });

// AFTER (live API) - shape stays identical
const res = await fetch('https://YOUR-PROJECT.supabase.co/rest/v1/site_content', {
  headers: { apikey: PUBLIC_KEY, Authorization: 'Bearer ' + PUBLIC_KEY }
});
this._shared = await res.json();   // same keys: works, journal, services, featured...
5
Make the CMS write. In TurtleLabs CMS.dc.html, the save / delete / featured / upload handlers currently update React state only (search for the (demo) toast strings). Replace those with Supabase insert / update / delete / storage.upload calls.
6
Replace the demo login. The CMS sign-in accepts anything. Swap it for Supabase Auth (email + password) and protect the write endpoints with row-level security so only signed-in admins can edit.
Why this is the light path: Supabase gives you the database, the API, file storage and auth without writing a server. The only code is the fetch/insert swaps above - roughly 1-3 days for a developer, and the front-end design is untouched.

4b. Email sending (workbook, playbook, booking)

A static page cannot send email itself - today the buttons download the PDF and show a "sent" confirmation only. To actually deliver mail, wire the capture forms to one of:

  • EmailJS - no backend, sends from the browser via a template. Fastest.
  • A Supabase Edge Function + Resend or SendGrid - stores the lead and emails the PDF as an attachment. More robust.
  • Your existing CRM / mailing tool's form endpoint.

The capture handlers to wire live in Turtle Labs Landing.dc.html: submitWorkbook, submitPlaybook, and the booking submit. They already collect the email - just POST it to your chosen service.

4c. Booking

Booking hands off to Calendly (calendly.com/turtlelabsdesign/30min). The on-page calendar prefills the date and email; the visitor picks the time on Calendly. Confirm the Calendly URL is final. No backend needed for this.

6. Hosting (with a developer)

This is a static front-end, so hosting is cheap and simple. Push the folder to any static host - all have free tiers and auto-HTTPS:

  • Netlify or Vercel - drag-and-drop the folder or connect a Git repo; deploys in seconds, custom domain in minutes.
  • Cloudflare Pages or GitHub Pages - equally free and fast.

The Supabase backend (Section 4) is hosted by Supabase separately; the site just calls its URL. Point your domain's DNS at the static host and you are live.

7. Go live without a developer or coding

You can launch a real, editable site yourself. The trade-off: you manage content in a hosted dashboard instead of this custom CMS screen. Two honest routes:

Route 1 - Publish the design as-is, edit content by asking (fastest)

1
Deploy the folder to Netlify: create a free account, drag the project folder onto the Netlify dashboard. You get a live URL immediately.
2
Connect your domain in Netlify (Domain settings - it walks you through the DNS records). HTTPS is automatic.
3
To change content, edit tl-content.js (it is plain, labelled data) and re-drag the folder, or ask us to update and redeploy. no code

Limitation: forms show the "sent" confirmation and download the PDF, but do not email until wired (Route 2 or a developer).

Route 2 - Managed CMS dashboard (fully self-serve, recommended)

1
Sign up for a no-code CMS - Sanity, Storyblok, or Webflow CMS. They provide a database, media uploads (image/video/PDF with their own compression + CDN), and a login, all through a web dashboard.
2
Recreate the content types in their dashboard to match this site: Work, Journal Article, Review, Logo (fields listed in Section 4, step 2). Their setup is form-based.
3
Add email + booking with no-code tools: EmailJS or the CMS's form feature for the workbook/playbook, and your Calendly link for booking.
4
The one code touch is connecting the site to the CMS's API (Section 4, step 4). Their docs walk you through it; if you get stuck, this is the single task worth a few hours of a freelancer.
Why a managed CMS matters for speed: Sanity/Storyblok/Webflow auto-serve optimized images from a fast CDN - the biggest real-world page-speed win, on top of the in-browser compression already built into the demo CMS.

8. Suggested launch checklist

  • Rename files to slugs; verify every menu, footer, and button link.
  • Finalize the 6 featured works and their order (CMS Featured screen or the featured line in tl-content.js).
  • Replace demo/placeholder figures in case studies with real numbers.
  • Wire the workbook, playbook, and booking forms to a real email service.
  • Stand up the database + real CMS login (or move to a managed CMS).
  • Add legal pages, SEO/OG tags, and analytics.
  • Test on mobile, tablet, and desktop; test light and dark themes.
  • Deploy to a static host, connect the domain, confirm HTTPS.
  • Do a full click-through of every flow on the live URL before announcing.
